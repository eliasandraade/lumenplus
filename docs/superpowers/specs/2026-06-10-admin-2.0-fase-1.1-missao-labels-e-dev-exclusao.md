# Spec Executável — Admin 2.0, Fase 1.1: Rótulos de "Missão" + Exclusão de DEV de membros

**Data:** 2026-06-10
**Status:** SPEC — nada implementado.
**Base:** Fase 1 já em produção (`527aa94`); auditoria e Product Definition do Admin 2.0.
**Motivação:** durante o QA da Fase 1, dois pontos surgiram:
1. Há **dois "Missão"** no painel que medem coisas diferentes (estrutura vs. perfil) → risco de interpretação.
2. Usuários com cargo **DEV** aparecem inflando contagens e listas de **membros reais** de ministérios/setores/conselhos (são contas de infraestrutura, não membros da comunidade).

**Restrições vinculantes:** sem migrations · sem tabelas novas · **sem alterar regras de permissão/acesso** (DEV mantém todo o acesso; muda só exibição/contagem) · sem tocar CPF/RG, H5/H6, Projeto de Vida · sem Analytics Missionais/eventos · sem tokens de tema · sem redesenho.

Três partes **independentemente deployáveis**:
- **Parte A** — rótulos de "Missão" (frontend-only, risco baixo).
- **Parte B** — excluir DEV das contagens/listas de **membros de unidade** (backend, risco médio).
- **Parte C** — excluir DEV de **todas as métricas globais** do dashboard (backend, risco médio). *(Decisão do Conselho/usuário em 2026-06-10: DEV é conta puramente técnica → fora de todo o dashboard, ficando apenas em `/admin/users`.)*

---

## PARTE A — Disambiguar "Missão" (frontend-only)

### Problema
- Em **"Vínculos e participação"**, a barra **"Missão"** = vínculos ativos a unidades de **tipo MISSAO** (estrutura organizacional). Vem de `by_unit_type`.
- Em **"Acompanhamento e interesse"**, o card **"Vieram de missão"** = perfis com a flag **`is_from_mission`** ("É de alguma missão?"). Vem de `from_mission`.
- Mesmo nome, fontes diferentes → confusão (confirmada no QA).

### Alterações — [lumen_mobile/app/admin/dashboard.tsx](../../../lumen_mobile/app/admin/dashboard.tsx)
| # | Alteração |
|---|---|
| A1 | Na renderização de `by_unit_type`, **sobrescrever o rótulo** quando `item.type === 'MISSAO'`: exibir **"Comunidades de Missão"** em vez de `item.label`. (Não depende do backend — override só de exibição. Demais tipos seguem com `item.label`.) |
| A2 | Renomear o card de perfil **"Vieram de missão"** → **"Membros vindos de missão"** (deixa explícito que é atributo declarado da pessoa, não estrutura). |
| A3 | (Opcional, clareza) Nota curta sob as barras de `by_unit_type`: *"Vínculos por tipo de unidade da estrutura."* |

**Sem mudança de backend, payload, permissão ou dado.** Puro texto/exibição.

### Aceite (Parte A)
- [ ] A barra de Missão em "Vínculos e participação" lê **"Comunidades de Missão"**.
- [ ] O card em "Acompanhamento e interesse" lê **"Membros vindos de missão"**.
- [ ] Nenhum outro tipo de unidade teve o rótulo alterado.
- [ ] `tsc --noEmit` limpo.

## PARTE B — Excluir DEV de "membros reais" (backend)

### Definição
- **DEV** = usuário com papel global de código `DEV` (`UserGlobalRole` → `GlobalRole.code == 'DEV'`).
- **Regra:** DEV **não** é contado nem listado como **membro real** de nenhuma unidade (ministério, setor, conselho, grupo, missão).
- **Somente DEV.** ADMIN/SECRETARY/ANALISTA/AVISOS **continuam** contando como membros (podem ser pessoas reais).
- **Não é mudança de permissão:** DEV mantém acesso, visibilidade e capacidade de ação inalterados. Muda apenas **onde DEV é exibido/contado como membro**.

### Escopo — onde excluir DEV (as 3 superfícies devem ficar consistentes)
| # | Superfície | Arquivo / função | Mudança |
|---|---|---|---|
| B1 | **Lista de membros da unidade** (modal Membros em Entidades) | `services/organization.py` → `get_org_unit_members` (~L580) | filtrar memberships cujo `user_id` é DEV |
| B2 | **Contagem de membros na árvore** ("X membros" em Entidades) | `routes/organization.py` → `get_organization_tree` / `build_tree` (~L247) | `active_member_count` ignora user_ids DEV |
| B3 | **Dashboard — vínculos/pessoas** | `routes/admin.py` → `total_active_memberships`, `people_active` (~L746–764) | `WHERE OrgMembership.user_id NOT IN (dev_ids)` |
| B4 | **Dashboard — por tipo de unidade** | `routes/admin.py` → `by_unit_type` (~L766) | idem (exclui DEV) |
| B5 | **Dashboard — top ministérios** | `routes/admin.py` → `top_ministries` (~L780) | idem (exclui DEV) |

### Helper compartilhado (DRY)
- Novo helper em `services/organization.py`: **`get_dev_user_ids(db) -> set[UUID]`** = `select(UserGlobalRole.user_id) join GlobalRole where GlobalRole.code == 'DEV'`.
- Reutilizado por B1, B2 (set em memória) e importado pelo dashboard (B3–B5) como subquery `notin_` (para não materializar em SQL).
- Uma fonte de verdade evita que árvore, lista e dashboard divirjam.

### Onde **NÃO** mexer (limites explícitos)
- **`/admin/users`** (Gestão de Usuários, lista global): DEV **continua aparecendo** — é o único lugar onde DEV permanece, para poder gerenciá-lo. (A regra é "não contar como membro/comunidade", não "sumir do sistema".)
- **Caminho de escrita / segurança:** `remove_member`, checagem de `last_coordinator`, convites, permissões — **inalterados**. A exclusão é só de exibição/métrica.
- **`/org/my/memberships`**: inalterado (usuário vendo os próprios vínculos).
- *(As contagens globais do dashboard **passam a excluir DEV** — ver Parte C.)*

### Riscos e mitigação (Parte B)
| Risco | Mitigação |
|---|---|
| **Números de membros vão cair** (vínculos, pessoas, contagem por unidade, ministérios) onde havia DEV | Esperado e desejado; documentar no changelog ("agora reflete membros reais") |
| Unidade cujo **único coordenador é DEV** passa a parecer sem coordenador | Comportamento correto (DEV não é coordenador real), mas **flag**: revisar se há unidades nessa condição antes do deploy |
| **Inconsistência write-path:** `last_coordinator` ainda conta DEV → possível demitir-se deixando só um DEV (oculto) como coord | Fora do escopo desta fase (não mexer em segurança de escrita). **Anotado** como follow-up se ocorrer na prática |
| Divergência entre árvore, lista e dashboard | Helper único `get_dev_user_ids` garante consistência |
| Performance (query extra de dev_ids) | 1 query pequena; conjunto DEV é minúsculo |

### Critérios de aceite (Parte B)
- [ ] DEV **não** aparece na lista de membros de nenhuma unidade (`/org/units/{id}/members`).
- [ ] `member_count` da árvore (Entidades) **não** inclui DEV.
- [ ] Dashboard: `total_active`, `people_active`, `by_unit_type`, `top_ministries` **excluem** DEV; os três batem entre si e com a árvore.
- [ ] **ADMIN não-DEV continua** contando/aparecendo como membro.
- [ ] DEV **continua** visível em `/admin/users` (Gestão de Usuários global).
- [ ] **Métricas globais de usuário/perfil:** excluem DEV conforme **Parte C** (não são "inalteradas"). **Convites:** inalterados.
- [ ] Permissões/acesso de DEV **inalterados** (suíte H5/H6 verde).
- [ ] Suíte backend completa verde + novos testes.

### Plano de testes (Parte B) — novo `backend/tests/test_dev_member_exclusion.py`
Padrão TestClient real (igual a `test_dashboard_phase1.py`):
- Seed: 1 unidade; 1 membro comum + 1 ADMIN-membro + 1 DEV-membro (todos ACTIVE).
- `GET /org/units/{id}/members` → retorna o comum e o ADMIN, **não** o DEV.
- `GET /org/tree` → `member_count` da unidade = 2 (não 3).
- `GET /admin/dashboard` → `total_active`/`people_active` não contam o DEV; `by_unit_type` e `top_ministries` idem.
- DEV em 2 unidades → não aparece em nenhuma; pessoas/vínculos coerentes.
- Sanidade: remover o papel DEV faz a pessoa voltar a contar.
- Authz: endpoints seguem exigindo os mesmos papéis (sem regressão).

## PARTE C — Excluir DEV de todas as métricas globais do dashboard (backend)

### Princípio
DEV é **conta puramente técnica** (decisão de 2026-06-10) → não representa a comunidade e deve sair de **todo** o dashboard. Junto com a Parte B, o efeito é: **o dashboard inteiro reflete só a comunidade real**; DEV permanece apenas em `/admin/users`.

### Por que precisa ser abrangente (não só o "total")
Se excluíssemos DEV só de `users.total` mas não dos breakdowns, o "X de Y (Z%)" deixaria de fechar (a base por catálogo poderia superar o total). Logo, **todas** as queries de usuário/perfil do `get_dashboard` excluem DEV de forma uniforme.

### Alterações — [routes/admin.py](../../../backend/app/api/routes/admin.py) `get_dashboard`
Aplicar o mesmo filtro `NOT IN (dev_ids)` (reusando o helper `get_dev_user_ids`, agora compartilhado por B e C) a:
| # | Métrica | Campo |
|---|---|---|
| C1 | Total de membros ativos | `users.total` |
| C2 | Novos (7d) e (30d) | `new_last_7d`, `new_last_30d` |
| C3 | Cadastros completos (base do "X de Y") | `complete_profiles` |
| C4 | Faixas etárias | `age_ranges` (datas de nascimento) |
| C5 | Geografia | `by_city`, `by_state` |
| C6 | Perfil vocacional | `by_life_state`, `by_marital_status`, `by_vocational_reality` |
| C7 | Acompanhamento e interesse | `with_/without_vocational_accompaniment`, `interested_in_ministry`, `from_mission` |

> Convites (`invites.*`): manter como está — convite não é "usuário"; um DEV raramente é alvo de convite e a métrica é de fluxo, não de população. *(Se aparecer convite a/por DEV distorcendo, tratar em follow-up.)*

### Aceite (Parte C)
- [ ] DEV não entra em `users.total`, `new_last_7d/30d`, `complete_profiles`.
- [ ] DEV não entra em faixas etárias, geografia nem nos breakdowns de perfil.
- [ ] Coerência mantida: bases dos "X de Y (Z%)" continuam fechando (nenhuma base de catálogo > total).
- [ ] Dashboard inteiro reflete só a comunidade real; DEV só permanece em `/admin/users`.

### Testes adicionais (no mesmo `test_dev_member_exclusion.py`)
- Seed com 1 DEV que tem perfil COMPLETE + cidade + faixa etária + realidade vocacional.
- `GET /admin/dashboard`: o DEV **não** aparece em nenhuma das métricas C1–C7; as bases continuam coerentes.
- Remover o papel DEV → a pessoa volta a contar em todas.

## Ordem recomendada de implementação
1. **Backend Partes B + C** (helper `get_dev_user_ids` + B1–B5 + C1–C7) — 1 commit (mesmo helper, mesma fase).
2. **Testes B + C** (`test_dev_member_exclusion.py`) — 1 commit; suíte completa verde local.
3. **Deploy backend** (Railway) + validação (health/openapi/headers/boot).
4. **Parte A frontend** (A1–A3) — 1 commit; `tsc` limpo.
5. **Deploy frontend** (Vercel).

> Parte A (frontend) é independente das B/C (backend) e pode ir junto ou antes. B e C compartilham o helper → mesmo commit/deploy de backend.

## Rollback
- Sem schema/migrations → `git revert` por parte.
- Backend (B+C) e frontend (A) revertíveis isoladamente; mudanças de backend são só **de valor** (contagens menores) + filtro em lista — sem mudança de shape do payload.

## Decisão registrada
- **2026-06-10:** DEV = conta puramente técnica → **Parte C aprovada** (excluir de todo o dashboard, não só de membro de unidade). Convites mantidos como estão por ora.
