## 1. Objetivo da Fase 1

Tornar **honestos e legíveis** os números que o Admin já mostra: corrigir fórmulas erradas (convites, ministérios, idade), explicitar bases de percentual, separar vínculos de pessoas, limpar geografia, eliminar dados mortos, trocar jargão técnico por linguagem de conselheiro, e consertar duas arestas de navegação/rotulagem (Aprovações invisível; labels de auditoria irreais). **Nenhuma métrica nova de missão** — só consertar o que existe.

## 5. Riscos e mitigação

| Risco | Mitigação |
|---|---|
| **Números vão mudar** (taxa de aceitação ↑, ministérios podem se dividir, perfis completos pode ↓) e parecer "bug" para quem acompanhava | Nota de comunicação: "os números mudaram porque agora estão corretos"; manter este spec como changelog citável |
| Janela de deploy: frontend novo + backend antigo → campos ausentes | Defaults defensivos no front (F1) **e** ordem de deploy backend→frontend |
| Supressão k esconder cidades legítimas pequenas | `K_MIN` como constante única e documentada; linha "Outras" preserva o total |
| GROUP BY id mudar ranking de ministérios homônimos | Esperado e desejado; citar no changelog |
| Tela Aprovações descoberta mas quebrada na web (Alert.alert) | F9 é pré-requisito de F8 — implementar juntos, nessa ordem |
| Regressão em authz (área sensível pós-H5) | Zero mudança em permissões; testes de regressão H5 existentes devem continuar verdes |

## 6. Critérios de aceite

1. `accepted + pending + declined + expired + cancelled == total` no payload e na UI.
2. `acceptance_rate == round(accepted/(accepted+declined)*100,1)`; `0.0` quando não há resolvidos.
3. Dois ministérios com mesmo nome em setores distintos aparecem como **duas linhas** com sufixo de setor.
4. `people_active <= total_active`; pessoa em 3 unidades conta 1 em pessoas, 3 em vínculos.
5. Nascido há exatos 18 anos **hoje** cai em "18-25" (não "<18"); caso bissexto não desloca bucket.
6. Cidades " Fortaleza " / "fortaleza" / "FORTALEZA" agregam numa só; nenhuma linha vazia; nenhuma cidade exibida com `count < K_MIN` (vai a "Outras").
7. `incomplete_profiles` ausente do payload; nenhuma referência no front (typecheck verde).
8. Todo percentual da tela exibe base no formato "X de Y (Z%)" ou rodapé "de N que informaram".
9. Entrada "Aprovações" visível para ADMIN/DEV no menu; ANALISTA segue vendo só Dashboard; aprovar/rejeitar funciona **na web** via modal inline.
10. Logs: as ações reais listadas na F7 exibem label pt-BR; nenhum label órfão de ação inexistente.
11. Suíte backend completa verde (baseline 159 passed) + novos testes.
12. Sem alteração em: permissões, CPF/RG, fluxos H5, Projeto de Vida, schema.

## 8. Plano de rollback

- **Sem dados/schema para reverter** (nenhuma migration). Rollback = reverter commits.
- Backend: `git revert` do(s) commit(s) B1–B8 → push → redeploy Railway (mesmo fluxo dos H5).
- Frontend: `git revert` F1–F9 → redeploy Vercel.
- Compatibilidade cruzada: front novo tolera payload antigo (defaults F1); front antigo tolera payload novo (mudanças aditivas) → **qualquer um dos lados pode ser revertido isoladamente**.

## 9. Ordem recomendada de implementação

1. **B1–B8** (backend, 1 commit) — payload completo.
2. **Testes backend** (commit 2) — suíte verde local.
3. **Deploy backend** (Railway) + verificação produção (front antigo segue funcionando).
4. **F1–F6** dashboard (commit 3).
5. **F7** logs + **F9→F8** aprovações (commit 4 — F9 antes de F8).
6. Typecheck + QA manual web.
7. **Deploy frontend** (Vercel) + smoke final.
